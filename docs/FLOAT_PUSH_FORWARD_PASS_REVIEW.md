## 折返原因

原全身入口在达到80°后，始终先导航到门前 `pass_pre_xy`，再导航到门后 `pass_through_xy`。本例首次达到80°附近，底座x≈2.504m，门参考x=2.5m，仍被要求返回门前x≈3.55m/y=-0.10m，然后前往门后x=1.10m/y=-0.10m。原 `navigation_command` 对大航向误差暂停前进并转向，因此出现先转近180°、回到门前，再转近180°穿门的动作。这来自原全身导航阶段，非IK或浮动底座执行API主动旋转。

另有相关边界问题：原通过侧按首次80°时的当前位置确定。浮动底座可能此前已越过门平面，导致门后目标反向。原浮动入口的 `compute_base_push_target` 则按初始heading计算推进终点，`trajectory_targets`在推门阶段直接插值底座位置，不包含原全身入口的门前重新对齐阶段。

## 最小修复

增加浮动后端参数 `--float_pass_mode forward`：

- 用初始接近侧确定通过目标，避免在门平面附近/已越过门平面时翻转目标。
- 80°后直接进入 `pass_through`，跳过门前 `pass_align`；继续使用原导航函数前往同一门后目标和原0.12m完成容差。
- 保留原80°条件、专家开门轨迹、相机、IK/伺服/门物理、开门后 `snap_arm_to_zero`、任务→DP覆盖→执行顺序。数据字段维度不变，执行profile另标记 `_forward_pass`，避免与旧版演示混用。
- 浮动后端默认forward，可显式指定 `--float_pass_mode source` 回放旧流程；原全身后端默认source。新模式是对全身通过阶段的修改，并未宣称完整复刻原浮动入口的推进插值轨迹。

CPU回归检查覆盖后端默认模式、源流程行为对照、门前/门平面/门后目标方向、相反接近侧，以及既有状态/分析检查。同seed14400这一例尚不代表多初态鲁棒性。

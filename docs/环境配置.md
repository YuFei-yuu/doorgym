## 50 系/Blackwell 与旧 Gym 栈不兼容：原因与修复

### 最初失败在哪里

本服务器实际是 RTX PRO 5000 Blackwell；本次处理的是其 `sm_120` 架构兼容问题，并没有逐一验证其他 RTX 50 系型号。

仓库 Isaac Gym 依赖 Python `>=3.6,<3.9`，提供 Python 3.6/3.7/3.8 的预编译绑定。最初在 Python 3.8 环境安装官方 `torch==2.4.1+cu121`，该 wheel 架构列表最高只有 `sm_90`，没有 `sm_120`。

当时 `torch.cuda.is_available()` 返回 true，Gym 的简单方块仿真也能运行，但执行真正的 CUDA 张量运算就失败：

```text
RuntimeError: CUDA error: no kernel image is available for execution on the device
```

因此，“能识别显卡”“Gym 能导入”或“方块能动”都不足以证明机器人控制、PyTorch 张量和相机链路可用。单纯安装更高版本官方 PyTorch 又会碰到旧 Gym 的 Python 3.8 二进制约束。

旧环境 `/data/zyf/video2door/.repro/envs/b1z1` 保留用于历史诊断，**不要继续用它运行当前任务**。

### 实际采用的解决办法

参考用户提供的 [CSDN 文章](https://blog.csdn.net/m0_56706433/article/details/148902144)，保留旧 Gym 所需的 Python 3.8，另建独立环境，使用能够编译 `sm_120` 的私有 CUDA 12.8，从源码构建旧版 PyTorch 2.3.1。

具体适配包括：

1. **CUDA 目录布局**：conda CUDA 开发包主要位于 prefix 的 `targets/x86_64-linux` 下。`prepare_toolchain.py` 在项目内生成 `/data/zyf/video2door/.repro/blackwell/cuda-12.8` 链接视图，为旧 CMake 提供常规的 `include`、`lib64`、`nvvm`、`bin` 路径，并补齐旧 NVTX 查找所需链接。
2. **计算能力解析**：旧 PyTorch 的 CMake 架构匹配只适合一位整数计算能力，补丁允许两位数计算能力，识别 `12.0`。
3. **扩展编译架构白名单**：在 `torch/utils/cpp_extension.py` 中允许 `12.0`，使 gymtorch 等 C++/CUDA 扩展不再拒绝该架构。
4. **cuDNN 查找**：适配 `FindCUDNN.cmake`，让它接受明确指定的版本化库文件 `libcudnn.so.9`；激活脚本明确设置私有 cuDNN 路径。
5. **编译器/ABI**：PyTorch 和 gymtorch 使用系统 `/usr/bin/gcc`、`/usr/bin/g++`，设置 C++ ABI 为 0，避免扩展链接不一致。
6. **构建范围**：只编译 `sm_120`，关闭分布式、NCCL/Gloo/MPI/Tensorpipe、Kineto、Flash Attention、memory-efficient attention 及部分 CPU 优化后端；保留本项目所需 CUDA、cuDNN、autograd 和 TorchScript。BLAS 使用 OpenBLAS。

私有环境变量的关键值：

```bash
CUDA_HOME=/data/zyf/video2door/.repro/blackwell/cuda-12.8
TORCH_CUDA_ARCH_LIST=12.0
CC=/usr/bin/gcc
CXX=/usr/bin/g++
CUDAHOSTCXX=/usr/bin/g++
```

完整变量应由激活脚本设置，不建议逐项手动拼接。

### torchvision 与 torchaudio 的处理

- torchvision 0.18.1+cu121 与定制 torch 的组合已通过项目实际使用的 CUDA resize 测试。其独立 CUDA 扩展，例如 NMS，未验证 Blackwell 兼容性，不能从 resize 通过推断全部算子通过。
- torchaudio 原 CUDA 12.1 wheel 会检查与 torch CUDA 12.8 的小版本不一致，因此改为官方 2.3.1+cpu wheel。项目不使用音频，CPU 版本已正常导入。
- 不要运行无约束的 `pip install --upgrade torch torchvision` 覆盖定制版本；后续增加依赖时使用当前约束文件并重新检查相关入口。

## 相机的独立问题：CUDA 与 Vulkan 多卡编号不一致

解决 PyTorch 后，GPU 相机仍出现过另一个问题，与 CUDA 内核架构缺失不同：

- `CUDA_VISIBLE_DEVICES` 限制了 CUDA 可见卡，但不会相应隐藏 Vulkan 设备。
- 当时选择物理 GPU 0 计算，但原始 Vulkan 设备 0 对应物理 GPU 7，导致相机跨卡导入显存，出现 `cudaImportExternalMemory` error 999。
- 在仅启用 NVIDIA ICD 的原始 Vulkan 枚举中，物理 GPU 0 对应索引 4。直接用 `graphics_device_id=4` 又触发旧 Gym 的 `invalid device ordinal`，因为 CUDA 只看到一张卡，合法逻辑编号只有 0。

实际修复是建立**项目私有 Vulkan 设备筛选层**，按 GPU UUID 匹配目标物理卡，只向当前进程暴露这一张 Vulkan 卡，让 CUDA 与 Vulkan 都把它编号为 0。

关键文件均在 `/data/zyf/video2door/.repro/blackwell`：

| 文件 | 用途 |
| --- | --- |
| `/data/zyf/video2door/.repro/blackwell/probe_vulkan.c`、`/data/zyf/video2door/.repro/blackwell/probe_vulkan` | 枚举 Vulkan 设备及 UUID |
| `/data/zyf/video2door/.repro/blackwell/vulkan_device_filter.c` | 私有层源码，仅筛选设备枚举，渲染和显存 API 仍由驱动执行 |
| `/data/zyf/video2door/.repro/blackwell/libvulkan_video2door_device_select.so` | 私有层编译产物 |
| `/data/zyf/video2door/.repro/blackwell/vulkan-layer/VkLayer_video2door_device_select.json` | 层加载描述 |
| `/data/zyf/video2door/.repro/blackwell/build_vulkan_filter.sh` | 构建探针和私有层 |
| `/data/zyf/video2door/.repro/blackwell/activate.sh` | 自动 UUID 匹配并为当前进程启用层 |

激活脚本设置 NVIDIA ICD、`VK_LAYER_PATH`、`VK_INSTANCE_LAYERS=VK_LAYER_VIDEO2DOOR_device_select`，自动求出 `VIDEO2DOOR_VK_DEVICE_INDEX`。对外的 `VIDEO2DOOR_GRAPHICS_DEVICE_ID` 为 0。

没有安装系统 Vulkan 层、替换驱动或修改 Gym 二进制。层的加载方式参考 Mesa 的设备筛选层，作用限于继承这些环境变量的进程。原始 Vulkan 索引可能变化，**不要把索引 4 写死**；每次通过激活脚本按 UUID 重新匹配。

若需要重建私有层：

```bash
bash /data/zyf/video2door/.repro/blackwell/build_vulkan_filter.sh
```

当前编译产物已经存在，无需为正常运行重复构建。
